# ADR-0004: безопасное слияние контактов

## Контекст

Один человек может попасть в систему несколько раз из разных источников. Жёсткое удаление дубля потеряло бы происхождение записи, историю связей и возможность расследовать ошибочное объединение. Простая ссылка дубля на другой дубль создала бы цепочки, усложняющие выбор контакта и конкурентную запись взаимодействий.

## Решение

`POST /api/v1/contacts/:sourceContactId/merge` выполняется идемпотентно в одной PostgreSQL-транзакции:

1. Блокирует граф слияний, исходный и целевой контакты, затем затронутые организации.
2. Запрещает self-merge, повторное слияние источника и выбор уже архивного целевого контакта.
3. Переносит активную contact–organization связь на целевой контакт. Если целевой уже связан с организацией, исходная связь закрывается через `valid_to`, а не удаляется.
4. Переносит все Interaction на целевой контакт.
5. Помечает источник полями `merged_into_id`, `merged_at`, `merge_reason`; ранее объединённые с ним контакты сразу перепривязывает к новому каноническому контакту, не оставляя цепочек.
6. Записывает AuditLog и OutboxEvent `contact.merged` до завершения IdempotencyRecord.

Создание ручного Interaction использует ту же advisory lock и разрешает архивный ID в актуальный канонический ID. Поэтому параллельное завершение задачи не оставляет новую историю на архивном контакте.

## Последствия

- Слияние не приводит к физической потере данных и остаётся расследуемым по аудиту.
- В рабочих выборках участвуют только контакты без `merged_into_id`.
- Операции слияния сериализованы; для административной команды это осознанный компромисс в пользу целостности.
- Обратное разъединение потребует отдельной контролируемой команды и не входит в текущий срез.
